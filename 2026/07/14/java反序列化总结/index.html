java反序列化入门篇-01-概念初相识

Java反序列化

也是学到java了，java确实方便，各种封装好的函数随便用，整一个就是调用调用再调用，但可以利用的地方也很多，果然便利是安全最大的敌人。

什么是反序列化

一步一步学过来的师傅们肯定对反序列化的定义和原理都不太陌生了，但想必以前都是接触的PHP反序列化。那java反序列化存在的意义又是什么呢？我们知道，当两个进程进行远程通信时，可以相互发送各种类型的数据，包括文本、图片、音频、视频等， 而这些数据都会以二进制序列的形式在网络上传送。那么当两个Java进程进行通信时，能否实现进程间的对象传送呢？答案是可以的。如何做到呢？这就需要Java序列化与反序列化了。换句话说，一方面，发送方需要把这个Java对象转换为字节序列，然后在网络上传送；另一方面，接收方需要从字节序列中恢复出Java对象。

序列化和反序列化原理

serialVersionUID

java的序列化和反序列化需要一个关键的东西：序列化ID(serialVersionUID)，它决定是否能够成功反序列化。这是因为java的序列化机制是通过判断运行时类的serialVersionUID来验证版本一致性的，在进行反序列化时，JVM 会把传进来的字节流中的serialVersionUID与本地实体类中的serialVersionUID进行比较，如果相同则认为是一致的，便可以进行反序列化，否则就会报序列化版本不一致的异常。而验证版本一致性是为了检查这个类是否存在过修改，若是修改过我们的反序列化数据就可能不适用于现在这个类。

序列化

对于序列化来说，最关键的是writeObject，序列化其实就是调用了这个函数而已，但里面到底发生了什么才是我们真正需要学习的

简单来说，序列化就是完成了以下步骤：

  • 将对象实例相关的类元数据输出。
  • 递归地输出类的超类描述直到不再有超类。
  • 类元数据完了以后，开始从最顶层的超类开始输出对象实例的实际数据值。
  • 从上至下递归输出实例的数据

反射

反射：程序运行期间，动态获取一个类的全部信息、并且动态调用它的构造方法、普通方法、成员变量的能力。正常代码是编译期就确定要调用哪个类、哪个方法；反射是运行时才决定操作哪个类、执行哪个函数。用我的大白话来说反射就是操作Class，所谓反射就是让我们能够重新对这个类进行操作。

反射初使用

先简单来read一下反射的使用过程：

  1. 获取 Class 对象：首先获取目标类的 Class 对象。
  2. 获取成员信息：通过 Class 对象，可以获取类的字段、方法、构造函数等信息。
  3. 操作成员：通过反射 API 可以读取和修改字段的值、调用方法以及创建对象。

从上面我们就能看出，使用的第一步当然是获取class对象，存在以下几种方法：

  • 类名.class

  • 对象.getClass()

  • 全限定类名字符串加载

    一般这个是最常用的，我们来详细讲讲

    每个类在 JVM 中都有一个与之相关的 Class 对象，Class对象就是一个类在 JVM 中的元数据模板。调用forname的过程中会读取class字节码，生成Class对象，且会自动执行静态代码块 static {}、给静态变量赋值。这里需要注意一个点，这个生成的是Class对象，并没有new实例。forname使用的时候要注意下面几点：在forName("com.xxx.User")中要用全限定类名（完整包名 + 类名），否则会报ClassNotFoundException；受当前线程类加载器限制，找不到类就抛出异常；基本类型无法使用forname进行反射，使用Class.forName("int") 将会报错，只能 int.class

动态代理

老规矩，我们在开始简述动态代理原理之前，先来讲讲动态代理是什么且正常情况有什么作用，知道它的用处才能带着思考学习原理。

我们在写了一个类后，在后续研发和拓展中，总是会需要添加功能，这个时候我们可能会想到修改源码或写个继承类，但如果我们需要多个继承类，且继承类之间其实改变不大，那我们的代码会太臃肿，维护难度会成倍增加，动态代理就是为了解决这种情况而诞生的。用一句话来总结：动态代理的作用是在不修改原有类源码的前提下，给现有方法增加“额外动作”。而动态代理的所谓动态就是在需要代理的时候再动态生成，我们来通过代码来看一下动态代理的实现。

在JDK动态代理中，要注意JDK动态代理必须要求目标类实现接口，原因是Proxy.newProxyInstance() 在运行时，会在内存中动态生成一个全新的类（这个类叫 $Proxy0）。这个新类已经被规定必须继承 java.lang.reflect.Proxy 这个父类。而Java 是单继承的。既然 $Proxy0 已经继承了 Proxy，它就不能再继承其他类了既然不能继承类，它怎么拥有方法呢？只能通过实现接口。因为 Java 允许实现多个接口。所以，JDK 代理生成的 $Proxy0 会实现传进去的Chef.class.getInterfaces()。当调用 proxy.serve() 时，$Proxy0 内部会通过接口方法表，精准地找到InvocationHandler.invoke(proxy, method, args)，proxy是代理对象，method是调用的方法，args是传入的参数。这个invoke()不是 JDK 的 Java 源码调用的，是运行时内存里动态生成的代理类（$Proxy0）的字节码，直接硬编码调用你的 handler.invoke ()。

动态代理的利用

我们来个栗子看看动态代理在反序列化中到底怎么用吧，毕竟这才是我们真正的目的

计算哈希值时，会调用 key.hashCode()。由于我们的 key 是一个动态代理对象，它实现了 IAttack 接口，而 hashCode() 是 Object 的方法，代理会对所有方法（包括继承自 Object 的方法）进行拦截。因此，hashCode() 的调用会触发 EvilHandler.invoke()，从而执行恶意代码。

在反序列化利用中，攻击者会构建一个代理对象，当这个代理对象的某个方法（如 toString(), hashCode()等）在反序列化或后续处理中被隐式调用时，其 invoke 方法就会被触发，从而执行攻击者预设的恶意代码

类加载机制

先来解释一下类加载机制吧

Java 文件编译后是 .class 字节码（一堆二进制数据）。类加载器就是 JVM 的户籍警，它的工作是：

把二进制字节码（byte[]）搬进内存，解析成 JVM 认识的方法区数据结构，最后生成一个 java.lang.Class 对象放进去。

写的类，如果不经过类加载，在 JVM 里就是一堆废纸。

其中类加载的过程包括了加载、验证、准备、解析、初始化五个阶段。

这边我们主要需要注意的就是初始化阶段，在初始化阶段，JVM 会执行 <clinit>() 方法。这个方法里包含两样东西：

  1. 静态变量的显式赋值：比如 static int a = 10;（把 0 变成 10）。
  2. 静态代码块 static {}：里面你写的所有逻辑。

在类首次被加载到JVM内存时会自动执行静态代码块，所以只能调用一次，各位师傅看到这里想必两眼放光了吧，都自动执行了，那如果在静态代码块中写入恶意方法，那不相当于想干嘛干嘛呗。但这里有个小tip：我们在静态代码块中只能调用静态方法，实例方法是没用的。

知道了静态代码块的好处，我们现在就要知道如何让它自动执行了，从上面各位师傅也可以明白下面我们就要知道如何初始化类:

  • Class.forName(“全类名”)

    这里要注意一个点，forName()的第二个参数默认为true，此时会初始化，但如果改为false则不会初始化

  • new创建类实例

  • 子类初始化，会先触发父类初始化

讲到这里，那就顺便提一下实例代码块（也叫构造代码块）吧

实例代码块在构造器被调用时会自动调用，下面是具体情况：

  • new创建类实例

  • 反射的 Constructor.newInstance()

  • 子类构造器隐式调用父类构造器

看完是不是觉得实例代码块的调用方式和静态代码块的调用方式非常的像，但这里最重要的区别就是静态代码块是在类被加载进JVM时调用的，而实例代码块是在构造器被调用时调用的。用new实例来举例，我们只有在首次以这个类为模版new实例的时候才会将类加载进JVM，后续如果再new由于我们已经将类加载进过JVM了，不会再次加载。而每次new都需要调用构造器来创建实例，所以每次new都会自动调用实例代码块。

实例代码块还有一个最大的好处是我们可以调用实例方法，那既然他的好处这么大，为什么我们不使用利用实例代码块，而是选择去使用静态代码块呢

我们在看利用点的时候不能仅仅看到有多大的利用能力，还要注意他的利用可行性，在这里我们明显可以看出静态代码块是更容易被利用的，我们只需要在类加载的时候就可以自动调用静态代码块，而实例代码块的利用硬性要求构造器运行，这就让我们的利用显得较为困难。且在标准的反序列化中，我们是没有利用构造器的。来看看简化的readObject

攻击者追求的是“只要反序列化就炸”，所以首选静态块。

双亲委派机制

当一个类加载器收到「加载 XX 类」的请求时，不会自己先去加载，而是先把请求丢给自己的父加载器；

父加载器再丢给它的父，一直递到最顶层的引导类加载器；

只有顶层父加载器说 “我找不到这个类”，当前加载器才允许自己去加载。

  • 三层加载器父子关系（从上到下）
  1. BootstrapClassLoader（引导加载器，最顶层，父为 null）
  2. ExtClassLoader（扩展加载器，父是 Bootstrap）
  3. AppClassLoader（应用加载器，你代码默认的加载器，父是 Ext）

但这里要注意，这里所谓的父子关系只是概念上的，并非真正继承的父子关系，而是采用通过 parent 成员变量建立的组合实现的。

为什么需要双亲委派机制

我们的Java在运行之前，首先需要把Java代码转换成字节码，即class文件。

然后JVM需要把字节码通过一定的方式加载到内存中的运行时数据区。

这种方式就是类加载器（ClassLoader）。

再通过加载、验证、准备、解析、初始化这几个步骤完成类加载过程，然后再由jvm执行引擎的解释器和JIT即时编译器去将字节码指令转换为本地机器指令进行执行。

我们在使用类加载器加载类的时候，会面临下面几个问题：

  1. 如何保证类不会被重复加载？类重复加载会出现很多问题。
  2. 类加载器是否允许用户自定义？
  3. 如果允许用户自定义，如何保证类文件的安全性？
  4. 如何保证加载的类的完整性？

为了解决上面的这一系列的问题，我们必须要引入某一套机制，这套机制就是：双亲委派机制。

虽然在反序列化的过程中你可能无法很好的利用上双亲委派机制，但对于我们理解JVM到底是在做什么以及理解其原理是非常有用的。
