Java反序列化Commons-Collections篇05——CC3链

java反序列化——CC3链

0x01 前言

也是来到CC3链，这次的链子和前面的不太一样了，也是绕了我几回，还是太菜了，继续加油。

CC3和前面讲的CC6与CC1的利用方式思路不太一样，CC6和CC1走到最后都是Runtime.exec() 进行命令执行的。而很多时候服务器的代码当中的黑名单会选择禁用 Runtime。而在CC3中，我们是通过动态加载字节码来实现自动执行恶意代码。

0x02 环境

  • jdk8u65
  • Commons-Collections 3.2.1

0x07 CC3自己的链子

我们前面的两种利用版本，都是利用了InvokerTransformer调用方法，但正版CC3链立志创出自己的一片天，于是改换门庭，用InstantiateTransformer走出了自己的道，下面就来研究一下

既然要开创自己的道，那首先要做肯定就是find Uasges，我们先去看一下哪里调用了newTransformer

来解释一下为什么我们最后利用的是TrAXFilter

  • Process：这个是 Java 进程类，代表系统启动后的进程。这里面的利用在main中

  • TemplatesImp：这里虽然调用了方法，但无法指定对象

  • TransformerFactoryImpl： 就算你构造这个类，反序列化之后不会主动调用 TemplatesImpl 的方法，没有触发点。

  • TrAXFilter：虽然这个类没有实现Serializable，但其调用是在构造函数，我们来看一下他的构造函数

    这里的templates是我们可控的，此时就可以掏出我们的InstantiateTransformer了

    我们在这里可以调用TrAXFilter的构造器并传参进行实例化，而这个类是实现了Serializable的，所以前面的问题就不再是问题。

0x08 思路梳理

CC3的区别

我们在画思维导图前，再梳理一下CC3和CC1与CC6在利用思路上的区别

CC1与CC6

CC1与CC6的侧重点一直都是利用InvokerTransformer的transform方法进行命令执行，但如果遇到黑名单的情况，我们命令执行的话可能就会受挫

CC3

CC3方法跳出了直接进行调用对象进行命令执行的逻辑，而是尝试加载外部字节码从而执行恶意代码的路子，CC3找到InstantiateTransformer的transform方法实例化我们想要的对象启动后半段链子。

这里是两种不同的利用思维，我的描述也许有一些词不达意，师傅们可以好好再品味一下，这对我们后续自己挖掘漏洞有很大帮助。
