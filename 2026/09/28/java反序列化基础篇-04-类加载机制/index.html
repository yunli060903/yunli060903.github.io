前言

本篇介绍的是类加载机制，既然是类加载机制，那我们需要研究的就比较底层了，需要根据源码打断点才能看清整个调用逻辑，单纯的文字知识了解，无法真正看到调用逻辑始终无法真正将这个概念植入心里，所以希望学习这块的师傅们可以自己打断点理解一下，当然我们不是只是简单的过一遍，而是真正理解他到底为什么会进到这一块代码。

类加载器

什么是类加载器

.java文件在编译后会生成.class字节码文件，但JVM无法直接读class文件，此时就需要类加载器出场了。类加载器会找到class字节加载进JVM内存，然后生成Class对象。还记得我们前面讲的类加载过程的五个阶段吗，其中包括加载、验证、准备、解析、初始化，类加载器就是在加载阶段进行工作。

类加载器种类

类加载器分以下几类：

  • 启动类加载器（根加载器）
  • 拓展类加载器
  • 应用程序类加载器
  • 自定义类加载器

启动类加载器（BootstrapClassLoader）

BootstrapClassLoader由 C++ 编写、内嵌在 JVM 内核中的类加载器，不属于 Java 体系里ClassLoader的子类，是整个双亲委派链的最顶端。在 Java API 中通常表示为 null，并且没有父加载器。在 JDK 8 HotSpot 中，它主要加载运行时核心类库（如 rt.jar）以及 -Xbootclasspath 指定路径中的类，但-Xbootclasspath这组参数在JDK9模块化后被移除。

扩展类加载器（ExtensionsClassLoader）

由 sun.misc.Launcher$ExtClassLoader 类实现，主要负责加载 %JRE_HOME%/lib/ext 目录下的 jar 包和类以及被 java.ext.dirs 系统变量所指定的路径下的所有类。Java 虚拟机会提供一个扩展库目录，此加载器在目录里面查找并加载 java 类。

应用程序类加载器（AppClassLoader）

JDK8：sun.misc.Launcher$AppClassLoader

JDK9~21：jdk.internal.loader.ClassLoaders$AppClassLoader

一般通过通过( java.class.path 或者 Classpath 环境变量)来加载 Java 类，也就是我们常说的 classpath 路径。通常我们是使用这个加载类来加载 Java 应用类，可以使用 ClassLoader.getSystemClassLoader() 来获取它。

自定义类加载器

除了 BootstrapClassLoader 其他类加载器均由 Java 实现且全部继承自 java.lang.ClassLoader。如果我们要自定义自己的类加载器，很明显需要继承 ClassLoader 抽象类。要实现自定义类加载器还需要重构loadClass和findClass两个重要方法

动态加载字节码

字节码是什么

Java 源代码（.java）经过编译器javac编译，不会直接翻译成操作系统 CPU 能识别的机器码，而是编译成一种中间的、跨平台的二进制指令，这个东西就是字节码，保存在 .class 文件里。

字节码的本质其实是一套 JVM 虚拟机的指令集，由一个一个 1 字节长度的操作码（opcode） + 可选操作数组成，所以叫字节码。

下面我们介绍多种能够用于反序列化攻击的，加载字节码的类加载器。

利用 URLClassLoader 加载远程 class 文件

在 JDK8 中，AppClassLoader继承自 URLClassLoader。因此，AppClassLoader 查找 class 文件的底层逻辑直接复用了 URLClassLoader 的实现，理解 URLClassLoader 的工作原理，就能理解 JDK8 默认应用类加载器是如何在类路径下搜索类的。

URLClassLoader 会读取java.class.path，把里面所有路径统一封装成java.net.URL对象。URLClassLoader 内部依靠URLClassPath，针对每一个 URL 自动选择对应的内部 Loader 去定位.class资源，判断规则如下：

  1. 如果 URL 结尾不带斜杠/：视为 Jar 文件，使用JarLoader，在这个 Jar 包内部检索 class；
  2. 如果 URL 结尾带有斜杠/，并且协议是file：代表本地文件目录，使用FileLoader，在本地磁盘目录查找 class；
  3. 如果 URL 结尾带有斜杠/，并且协议不是file（如 http）：使用通用基础 Loader，支持从远程网络位置读取 class 字节。

利用 ClassLoader#defineClass 加载字节码

不管是加载远程 class 文件，还是本地的 class 或 jar 文件，Java 都经历的是下面这三个方法调用。

前面我们的学习中或多或少都有提及上面的方法

  • loadClass是 ClassLoader 里核心入口方法，双亲委派逻辑写在这个方法里面。如果父加载器全都找不到，则调用findClass()，由当前类加载器自己去找字节码

  • findClass只负责根据类全限定名，找到.class 字节数组 byte []**，**不负责双亲委派，不负责把字节交给 JVM 生成 Class。 找到字节之后，在 findClass内部调用defineClass。

  • defineClass负责接收 class 字节数组byte[]，校验字节码合法性，把字节码转换成 JVM 里面的 Class 对象。

所以可见，真正的核心是defineClass，因为他的作用是将字节码转变一个Java类。

最终实现转变的ClassLoader#defineClass是native方法，具体实现在JVM由C语言实现，我们在一般反射调用的defineClass方法是下图这个

利用 BCEL ClassLoader 加载字节码

  • 什么是 BCEL？

BCEL全称为Byte Code Engineering Library，它是一个pache Commons 字节码工程库，是老牌 Java 字节码处理工具库，用来读取、解析、修改、在内存动态生成 Java .class 字节码

我们可以通过 BCEL 提供的两个类 Repository 和 Utility 来利用： Repository 是BCEL 里用来缓存、查找已经解析好的JavaClass对象； Utility 用于将原生的字节码转换成对象

这里由于原生的JDK包中可能在下载的时候没有将Utility类带入，使用代码的时候会找不到，这边建议引入Apache Commons BCEL 库
