这是我们学习的第二个链子——CC6，CC6的利用范围比CC1要大很多，CC6不受jdk版本的限制，只要Commons-Collections小于等于3.2.1都可以。

0x04 奇怪问题

  • 怪问一：在serialize(map2);打断点时，我们debug直接就调出了计算器，且逐步下一跳还是抛出和上文一样的问题
  • 怪问二：在unserialize("ser.bin");打断点debug也会直接调出计算器，且下一跳后又一次调出计算器
  • 怪问三：在fieldfactory.set(lazymap,chainedTransformer);打断点后逐步下一条无法调出计算器，进程正常结束

其实上面的三个问题究其原因都是因为IDEA给我们埋的坑

探究怪问一

IDEA 在进行 debug 调试的时候，为了展示对象的集合，会自动调用 toString() 方法，所以在创建 TiedMapEntry 的时候，就自动调用了 getValue() 最终将链子走完，然后弹出计算器。

按照其他师傅所说，我们在FIle—>Settings—>Debugger—>java中关闭“toString”即可，但实际操作下来我发现问题依旧存在，好像是因为我们的调试面板在呈现我们现在的value时依旧会自动调用toString()，但这玩意关不掉，即使选了不呈现Variables还是在我们看不见的地方偷偷调用toString()，有师傅知道如何解决还请指教

探究怪问二

与上一个问题有关，debug时自动调用toString()调用一次，在unserialize根据我们写的链子又调用了第二次

探究怪问三

多次调试后我注意到我们的map对象中始终存在"aaa"这个key，按道理来说我们在remove("aaa");后这个值就该消失了，但并没有。这个值没有消失造成的影响会是什么我们去看一下

如果“aaa”一直存在map.containsKey(key)返回值就为true，无法进入下面的逻辑，直接return map.get(key);，导致transform无法执行，链子永远无法触发。

expMap.put(tiedMapEntry, "bbb") 这个 put，操作的是外层 expMap（HashMap）； 而我们 hashMap.remove("key") 删除的，是内层 LazyMap 包装的底层 hashMap。这是两个完全独立的 Map！不要搞混！

我们在map.remove("aaa")打个断点debug一下，我们在过程中Alt+F8执行代码检查我们的“aaa”到底有没有成功删除

很明显看到我们其实在containsKey("aaa")的检验下依旧返回了true，这还是IDEA的debug环境下的坑，IDEA 调试器在读取对象的时候，触发了lazymap.get("aaa")，又执行 factory，重新 put (“aaa”,1) 到底层 map，所以我们最终无法调出计算器。这里写了一份测试EXP可以更直观的观察在运行系统和调试系统的不一样

图中我们可以直接看到我们在调试环境中aaa的判断一直为true，但在直接运行的情况下remove删除后aaa就已经在内存中消失了，且成功调出计算器。
